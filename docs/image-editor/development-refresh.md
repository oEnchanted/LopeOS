# Development refresh behavior

The running development server uses Vite and React Fast Refresh. The Image Editor previously exported component functions together with newly allocated arrays, objects and helper functions from `dialogs.tsx`, `tools.tsx`, `panels.tsx` and `menus.tsx`. React's refresh validator rejects changed noncomponent exports, so edits to those UI modules invalidated their parent boundary. Filter names were one concrete example.

Runtime metadata now lives in `filter-model.ts`, `tool-model.ts`, `panel-model.ts` and `menu-model.ts`. The four UI modules export components only. Type-only exports are erased and do not affect the boundary. `node tests/image-editor/hmr-browser.mjs` uses the real Vite/React runtime with isolated update messages: four UI updates preserve an open filter dialog, its radius value and document revision. Its control restores the old string-valued filter-name export and reproduces the incompatible-export invalidation. No source files are modified by this test, and no update is broadcast to the shared server's other browsers. The report is `hmr-verification.json`.

This removes avoidable UI invalidations. Editing a component's hook signature can still cause a legitimate development remount. Vite also reloads after its server disconnects/restarts, an explicit full-reload message, an initial error-overlay recovery, or some circular-import failures. Session recovery preserves editor documents, history and views through remounts/reloads; transient dialogs may close during a genuine remount. A production build does not run the development HMR client.

The repository's application-level `location.reload()` calls are explicit actions: Settings' safe reload, a completed backup restore, and a factory reset. The Settings version check is button-driven and does not poll or automatically reload. The shell keeps minimized windows mounted using `display: none`; focusing/switching apps retains their keyed window IDs. Its application error boundary displays a retry button rather than automatically refreshing. These findings identify a plausible and reproduced development trigger, not proof of the cause of every user-reported refresh.
